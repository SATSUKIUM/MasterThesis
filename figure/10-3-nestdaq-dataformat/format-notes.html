4. サイズと個数の関係

以下はV3のHBDが2 wordで、通常のデータソースだけが存在し、ソースごとにH個のHBFが揃う代表例。Ds,jをDAQ word数、njをHBF jのtrigger数とする。制御word、既存METAソース、追加情報がある場合はその分を数える。

対象非圧縮の実byte数意味
FEEのheartbeat区間8Ds,j + 16DAQ words + HBD1/HBD2
HBF16 + 8Ds,j + 16HBF Headerを追加
STF48 + Σj HBFs,j単一ソースのHBF列
TFBuilder出力TF24 + Σs STFs複数ソースを集約
LogicFilter追加部分56 + Σj(16 + 8nj)suppressionなしの場合の増分。実装のFilter.length値とは差がある
SlicerのMETA TFj24 + 56 + 16 + 8nj + 80S80＝STF Header 48 + HBF Header 16 + HBD 16
SlicerのSLICE TF24 + 80S + 8ΣsDwindows窓内hitとHBDを残す
後段FilterのMETA TF24 + 80SFilter/Trigger情報を除去
FileSink出力304 + Σ(保存するTFの実長) + 304非圧縮・通常終了時の論理構成

Slicerは不要な時間領域を除く一方、TF/STF/HBFのHeaderを複製し、重なる窓のhitも複製し得る。そのため、切り出し後の総データ量が必ず小さくなるとは限らない。trigger密度・窓幅・ソース数によって決まる。

5. 実装を読む際の注記

構造の意図と、今のソースが書くフィールド値を分けて整理する。以下はソース上の観察であり、実データでの発現確認や修正は今回行っていない。

項目コードで確認したこと資料・解析への影響
Filter.lengthAddFilterMessageはlength計算でtriggerをsizeof(uint32_t)＝4 Bとして数える。一方、出力とTrgTimeHeader.lengthは8 B/trigger。{{LogicFilter/LogicFilter.cxx|flt_datasize +=|該当箇所}}非suppression時のFilter.length初期値は実長より4Σnj B短くなる。TF全長は出力partサイズから再計算。SlicerのMETA生成ではFilter.lengthも再計算される。
numMessagesSTFBuilderはSTF Headerを除くpart数。LogicFilterのFilter Headerは自分を含むpart数。SlicerのSLICE STFは2に設定。META生成ではコピー元の値が残る。{{STFBuilder.cxx|stfHeader->numMessages|STFBuilder}} / {{TimeFrameSlicerByLogicTiming.cxx|stfh->numMessages = 2|Slicer}}一律に「HBF数」と訳さず、生成したデバイスごとの意味を併記する。特にシリアライズ後のレコード数とは区別する。
timeUSecSTFBuilderはgettimeofdayのtv_usec、LogicFilterはepochからの総µs。{{STFBuilder.cxx|stfHeader->timeUSec|STF}} / {{LogicFilter/LogicFilter.cxx|std::chrono::microseconds>(d)|Filter}}同名でも意味が違う。Filterの時刻をtimeSec + timeUSec/10⁶として加算すると二重計上になる。
Header内typeTFにframework状態フラグがある一方、Slicerと共通FilterはMETAと直接等値比較し、SlicerはMETA/SLICEで上書きする。資料のMETA/SLICE図は通常のtype値を対象にする。上位状態bitを含む入力の伝播は別途確認する。
SLICEのHBF length更新Slicerのhbfhidx位置をSubTimeFrame::Header*へcastしてlengthを書いている。{{TimeFrameSlicerByLogicTiming.cxx|auto hbfh = (SubTimeFrame::Header*)|該当箇所}}現在は両Headerのlengthがoffset 8なので同じ場所を更新する。HBFの構造がSTFと同じという意味ではない。
再出力時のlength共通Filterが明示的に再計算するのはTF.length。STF/HBF Headerはコピーする。{{FilterTimeFrameSliceABC.icxx|tf.GetHeader()->length =|TF全長更新}}派生ProcessSliceでHBFデータ数等を変更する場合は、下位Headerのlength更新責任も確認する。
FileSink Header/Trailertime_tを含む。HeaderとTrailerは同じフィールド構成だが値は異なる。304 Bはこの環境では検証済み。ファイルの移植性を考えると固定幅のwire型とABI依存の宣言を区別する。

6. 図・本文の編集と再生成

原本は次のテキストファイル。生成SVGは独立したベクター図として利用できる。色はKeynoteの配色に合わせ、各段階の箱・Header・payloadは図形と文字で作っている。

Noto Serifの採用とフォント設定

図だけをNoto Serifに固定。本文はRobotoとHiragino Sans系の設定を維持。通常体・太字・斜体を埋め込み、単独SVGもNoto Serifで生成する。日本語本文は日本語フォントへフォールバックする。

比較用のRoboto / Lato / Noto Serifと選択UIの実装は残してある。appearance.json の show_font_selector を true にして再生成すると選択欄を再表示できる。既定フォントは default_font_id: "noto-serif"。現在のHTMLには選択UIと切替スクリプトを出力していないが、3書体の埋め込みは保持している。

SVGの変数は <tspan font-style="italic"> で斜体にできる。この資料ではH、S、j、nj、kjだけを斜体にし、添字は小さく下げる。max-hbfなど実際の設定キーやHeader名は立体のままにする。埋め込んだ実際の斜体フォントを使用する。

3書体のフォントデータをHTML内の@font-faceに埋め込み、図もinline SVGとして配置した。HTMLは本文と全図の表示に必要なフォント・図形を含み、ネット接続なしで閲覧できる。単独配布用の各SVGにも@font-faceのdata URLでNoto Serifの通常体・太字・斜体とライセンスを埋め込んでいる。文字はテキストのままなので後から編集できる。

フォント原本はRoboto-Variable.ttf。このMacにあるRoboto 3.015を変更せずコピーした。SIL Open Font License 1.1を同梱。Robotoは日本語グリフを持たないので、日本語本文はHiragino Sansなどへフォールバックする。Robotoは比較候補として保持する。採用中の図はNoto Serifで表示する。埋め込みフォント名は専用の NestDAQ Roboto として登録し、OS側の同名フォントとの混同を避ける。図はRegular（weight=400）、標準幅（wdth=100）を明示している。

appearance.jsonのfont_choicesが選択肢と各書体の通常体・太字・斜体ファイル、svg_font_family / html_font_familyが表示に使うフォントを指定する。別フォントに変える場合は両方を対応させて再生成する。concept_font_size=28、depth_font_step=3、min_font_size=13で、概念の外枠から深さごとに文字を小さくする。実レコードの文字はその階層の概念名より2小さくし、下限を設ける。

Google Slides上の表示との見た目の差は、使用版・weight・文字サイズ・表示倍率・描画環境も照合が必要。この資料は同梱のRoboto 3.015のRegularを使い、Google Slidesが実際に選択したフォント版や太さとの一致までは確認していない。フォント比較見本では同じ文字列をRegular/Medium/BoldとHelveticaで比較できる。

ブラウザのWebフォント表示はSVGの@font-faceに基づく。外部エディタやSVG→PDF変換器によっては埋め込みWebフォントを読まない場合があるので、その場合は同梱TTFを使う環境で変換する。フォント変更後は文字幅が変わるため収まりを確認する。
